## 2026-09-03 — Migration order: membership helpers can't live where docs/07 §2 puts them
**Context**: docs/07 §2 specifies `app.my_household_ids()`, `app.is_member()`, `app.can_read()` as part of the same "helpers" migration as the enums (my suggested split's `01_enums_and_helpers.sql`). `my_household_ids()` is `language sql` and selects from `household_members`. Verified empirically against a real Postgres 16 instance: unlike PL/pgSQL, a `LANGUAGE SQL` function body is parse-analysed at `CREATE FUNCTION` time, so defining it before `household_members` exists fails with `relation "household_members" does not exist` — it is not a matter of statement ordering within one transaction, it is a hard requirement that the table already exist.
**Options**: (a) Keep the literal file split and make `my_household_ids()` `language plpgsql` instead of `sql` (plpgsql bodies are not parse-analysed at creation time) — but the exact function bodies are given verbatim in docs/07 §2 as `language sql`, and rewriting them changes the shipped contract for no functional gain. (b) Move `households`/`household_members` into `01_enums_and_helpers.sql` ahead of the helpers — but the suggested split explicitly separates "enums and helpers" from "households and profiles", and enums has no reason to own a tenant table. (c) Move `my_household_ids()`/`is_member()`/`can_read()` into `02_households_and_profiles.sql`, right after `household_members` is created, keeping `01_enums_and_helpers.sql` to only `app.nl_date()` (no table dependency) and the trigger functions (all `language plpgsql`, which — verified the same way — do *not* require their referenced tables to exist at creation time, only at first execution).
**Decision**: (c). `01_enums_and_helpers.sql` keeps `app.nl_date()` and the four trigger functions verbatim; `app.my_household_ids()`/`app.is_member()`/`app.can_read()` moved to `02_households_and_profiles.sql`, defined immediately after `household_members`, before any policy that calls them.
**Consequence**: The two files' contents differ from docs/07 §2's literal grouping, but every function's SQL body, name and signature is unchanged from the spec. Both files were run end-to-end against a real Postgres 16 instance (extensions, `pg_cron` included) to confirm the reordering is sufficient and no other forward reference exists in the split.
**Specs touched**: docs/07 §2

## 2026-09-03 — Household/member creation: no direct client insert, a metadata-driven signup trigger instead
**Context**: docs/06 §3 says every user gets a household "created on signup"; docs/07 §4 says household_members insert/delete is owner-only. Neither doc specifies the actual creation mechanism, and a naive RLS insert policy on `households`/`household_members` can't express "the very first membership row of a brand-new household" without a bootstrapping loophole (an `is_member`/`is_owner` check is always false before any membership row exists).
**Options**: (a) A permissive `households`/`household_members` insert policy with a carve-out for "creating your own first household" — fragile, hard to make airtight against abuse. (b) A `security definer` RPC the client calls right after signup. (c) A trigger on `auth.users` (`app.handle_new_user()`, `security definer`) that creates the profile, the household and the owner membership row atomically, with `households`/`household_members` insert denied outright (`with check (false)`) for ordinary authenticated clients — matching docs/07 §4's "only owner may insert" for every *subsequent* member, since the owner's own row never goes through that policy at all.
**Decision**: (c), extended so the trigger reads two optional keys off `auth.users.raw_user_meta_data` — `household_id` (use this id instead of a random one) and `join_household_id` (join an existing household as `member` instead of creating a new one) — because docs/24 §2 and docs/19 §3 require the local dev fixtures to have specific, predetermined household ids and a real multi-member household (Bram & Fleur), which is otherwise unreachable through this trigger design.
**Consequence**: `households`/`household_members` insert is `with check (false)` for the authenticated role; the owner adding a *second* member still goes through the normal `app.is_owner()`-gated insert policy, proven in `supabase/tests/002_rls_household_identity.sql`. `join_household_id`/`household_id` in signup metadata are only ever populated by our own code (the dev seed, or a future invite Edge Function that has already verified the inviter) — never taken from arbitrary client-supplied signup metadata without that server-side check, since GoTrue signup metadata is otherwise user-controlled.
**Specs touched**: docs/06 §3, docs/07 §4, docs/19 §3, docs/24 §2

## 2026-09-03 — `scope='personal'` needs an owner column even where docs/06 doesn't list one
**Context**: `budget_lines`, `recurring_series` and `obligations` each have a `scope scope_kind` column per docs/06 §7–§8, but none of the three has an `owner_user_id` in that doc's column list. `app.can_read(h, s, owner)` — the standard predicate every other scoped table uses — is meaningless without an owner to compare against `auth.uid()` when `s = 'personal'`. Every other scope-bearing table in docs/06 (`bank_accounts`, `transactions`, `envelopes`, `rules`, `income_events`) does carry one.
**Options**: (a) Leave no owner column and let `personal` scope on these three tables mean "visible to the whole household" in practice (i.e. dead code) — silently weakens a documented scope value. (b) Add `owner_user_id`, nullable, required exactly when `scope = 'personal'` (a check constraint), consistent with every other scoped table. (c) Drop `personal` as a legal scope for just these three tables — contradicts the `scope_kind` enum being shared across all of them per docs/06 §3.
**Decision**: (b). Added `owner_user_id uuid references auth.users` (nullable) to `budget_lines`, `recurring_series` and `obligations`, with `constraint ..._personal_owner_ck check (scope <> 'personal' or owner_user_id is not null)`.
**Consequence**: These three tables' column lists now include one field beyond docs/06's abridged listing. This was necessary to make the required pgTAP proof — "a personal-scoped row is invisible to another member of the same household" — meaningful for every tenant table, not just the ones docs/06 already fully specified. Revisit if a future spec update defines these columns differently.
**Specs touched**: docs/06 §7, §8; docs/07 §4

## 2026-09-03 — Child tables without their own `household_id`: RLS via a join to the parent
**Context**: `transaction_splits`, `split_participants`, `series_occurrences`, `obligation_instalments`, `envelope_contributions` and `balances` all have column lists in docs/06 (§4, §7, §8) with no `household_id`/`scope` of their own — tenancy is only reachable through their parent row (`transaction_id`, `series_id`, `obligation_id`, `envelope_id`, `account_id`).
**Decision**: Their RLS policies are `exists (select 1 from <parent> p where p.id = <child>.<parent>_id and app.can_read(p.household_id, p.scope, p.owner_user_id))` (or `app.is_member()` for parents without a scope, e.g. `bank_accounts` for `balances`) rather than a denormalised `household_id` column repeated on the child. `attachments` is the one exception with a real `household_id` column (docs/06 §9 lists it explicitly) — its policies still join back to `transactions` rather than trusting that column alone, because a transaction can be `scope='personal'` and an attachment on a personal transaction must be exactly as private as the transaction itself; trusting `attachments.household_id` in isolation would leak personal-transaction attachments to the whole household. Proven in `supabase/tests/004_rls_child_tables.sql`, including the personal-transaction-attachment case specifically.
**Consequence**: These six tables' "four policies" are join-based rather than the `app.can_read(household_id, scope, owner)` one-liner used elsewhere; the RLS coverage checker treats this as equivalent since it only checks for a `create policy ... for <cmd>` per table, not the predicate's shape.
**Specs touched**: docs/06 §4, §7, §8, §9

## 2026-09-03 — `sync_jobs`: `household_id` added, `from`/`to` renamed
**Context**: docs/08 §"initial syncs are chunked into a queue table `sync_jobs(id, connection_id, account_ref, from, to, cursor, state, attempts)`". `from` and `to` are reserved words in Postgres's grammar and cannot be used as bare column names. Separately, docs/14 has the client "poll `sync_jobs` every 5s" as the realtime fallback for sync-progress UI, filtered by household — which needs a column to filter on without forcing a join through `bank_connections` inside the RLS policy.

Read-only to the authenticated role either way — all writes are service-role-only (the sync Edge Function).
**Consequence**: `sync_jobs`'s column list differs from docs/08's parenthetical listing in these two respects; the RPC/edge-function contract for enqueuing a sync job (out of `supabase/**`'s scope) must populate `household_id` from the connection it is syncing.
**Specs touched**: docs/08 §"Edge Function hard timeout", docs/14 §"Realtime"

## 2026-09-03 — Defense-in-depth: every policy scoped `to authenticated`, every table gets an explicit `revoke ... from anon`
**Context**: docs/07 §4: "No table is readable by the anon role." A Supabase project's default platform bootstrap grants broad table-level `SELECT/INSERT/UPDATE/DELETE` to both `anon` and `authenticated` and relies entirely on RLS policies to narrow actual access. A `create policy ... using (true)` with no `to` clause applies to *every* role that reaches it, `anon` included — for a table like `nibud_reference` ("readable by all authenticated users"), an unscoped policy would also make it readable by `anon`.
**Decision**: Every `create policy` in every migration is written `to authenticated` explicitly (never unscoped, never `to anon`), and every tenant table additionally gets `revoke all on table <t> from anon;` right after its `create table` — so even if a future migration ever adds an `anon`-permissive policy by mistake, or the platform's default grants change, `anon` still has no table-level privilege to exercise it with.
**Consequence**: Verified directly: `set role anon; select * from categories;` returns `permission denied for table categories`, not zero rows — a stronger guarantee than RLS filtering alone. No behavioural change for `authenticated`.
**Specs touched**: docs/07 §4

## 2026-09-03 — pgTAP test file fixture convention
**Context**: `supabase/tests/*.sql` needs a way to impersonate different users under RLS. Supabase's real `auth.uid()` reads `request.jwt.claim.sub` from the Postgres session's GUC settings (set by PostgREST from the caller's verified JWT).
**Decision**: Every test file creates its own throwaway `auth.users` rows (triggering the real `app.handle_new_user()` signup path — extra, free coverage of that trigger in every file) and impersonates a user with `select set_config('request.jwt.claim.sub', '<uuid>', false); set role authenticated;` / `reset role; select set_config('request.jwt.claim.sub', '', false);` around each assertion block. `is_local` is `false` (session-scoped), not `true` (`SET LOCAL`-equivalent, statement-scoped) — the latter silently resets before the *next* statement even inside one open transaction, which would make every "as user X" block after the first see no JWT claim at all. Each file is a `BEGIN; select plan(n); ...; select * from finish(); ROLLBACK;` block, so fixtures never leak between files or into the seeded dev data.
**Consequence**: Any new pgTAP test file should follow this exact pattern. `select * from finish();` is pgTAP's own required idiom, not a `SELECT *` on a real table — the repo's "no `SELECT *`" rule doesn't apply to it.
**Specs touched**: docs/19 §1, `.claude/rules/08-security.md`

## 2026-09-03 — period anchor clamp range & mid-period kind-change semantics
**Context**: docs/10 §1 describes `custom_month`'s anchor day as "1–28" in prose, but §11's test matrix explicitly requires a case with the anchor set to 31 (clamped down in short months), and also requires a case where the household's `period_kind` changes mid-period (an ongoing period must "close" cleanly on the change date rather than silently keep using the old kind's boundaries).
**Options**: (a) Enforce the literal "1–28" range with a validation error for anchors 29–31 — contradicts §11's own required test case. (b) Silently widen the accepted range to 1–31 and clamp per-month via `Math.min(anchorDay, daysInMonth(...))` (already required for 29–31 in short months anyway, since day 30/31 doesn't exist in February). (c) For the kind-change case, mutate `periodFor`'s signature to take a "previous period" — but `periodFor` is meant to be a stateless pure function of `(date, config, today)` per its literal signature, so this would break every other call site.
**Decision**: (b) for the anchor range — `HouseholdPeriodConfig.anchorDay` accepts 1–31, and `clampedAnchor()` clamps to the target month's actual length for every month, not just February (already needed for e.g. anchor=31 in April). For the kind-change case: added `closePeriodOnKindChange(period, changeDate)` as a second, separate pure function — given the period that was open under the *old* config and the date the household's config changed, it returns that period truncated to end on `changeDate`. The caller (outside `packages/shared`, since it needs to read/write the stored period boundary) is responsible for detecting the config change and calling this once, then computing the new period going forward with `periodFor` under the new config as normal.
**Consequence**: `periodFor` itself stays a pure function of the *current* config only — it has no memory of a previous config and cannot detect a change by itself. Mid-period kind changes are only handled correctly if the caller calls `closePeriodOnKindChange` at the right moment; this is documented in the function's own doc comment. Revisit if a future spec gives `periodFor` an explicit "previous period" parameter instead.
**Specs touched**: docs/10 §1, §11

## 2026-09-03 — `carryInto`'s literal two-argument signature keeps an unused parameter
**Context**: docs/10 §3.4's pseudocode calls rollover as `carryInto(nextLine, prevLine)` — a two-argument call where the *result* is what the next period's opening balance should be. The three rollover modes (`none`, `carry_all`, `carry_deficit`) are computable entirely from `prevLine` (its target minus its actual spend/contribution) — `nextLine` is never read by any of the three branches.
**Options**: (a) Drop `next` from the signature entirely, since it's provably unused — but this deviates from the doc's literal call-site shape and would silently break if a future rollover mode genuinely needs to read the next period's own starting state (e.g. a mode that resets to a fixed number regardless of history). (b) Keep both parameters, with `next` prefixed `_next` (an intentionally-unused parameter, not a mistake) and a comment pointing at the doc's call-site shape as the reason it's still there.
**Decision**: (b). `carryInto(_next: BudgetLine, prev: BudgetLine): Cents` — the leading underscore satisfies `noUnusedParameters` deliberately rather than by exemption, and the doc comment explains why the parameter exists despite being unused today.
**Consequence**: If a future rollover mode is added that genuinely needs `next`'s own fields, drop the underscore and start reading it — no signature change needed then.
**Specs touched**: docs/10 §3.4

## 2026-09-03 — `recycle` cadence
**Context**: `docs/06`'s `cadence` enum includes `irregular` (docs/10 §11's "potje target date in past" / "target reached early" cases exercise `recycle`, which internally steps a due date forward by one cadence via `addCadence`). `addCadence` has no defined meaning for `irregular` — there is no fixed interval to step by.
**Decision**: `addCadence(date, 'irregular')` is a no-op, returning `date` unchanged rather than throwing or guessing an interval. `recycle` on an `irregular`-cadence potje therefore always recomputes `expectedByNow`/`behindBy` against the same due date until something external (the caller, based on user input) sets a new one — treated as "no fixed schedule to recycle toward" rather than an error state.
**Consequence**: An `irregular` potje never auto-advances its own due date through `recycle`; this must be surfaced as a caller-side UI affordance ("set a new target date") rather than silent automatic behaviour. Revisit if docs/06 ever defines a concrete stepping rule for `irregular`.
**Specs touched**: docs/06 §"cadence", docs/10 §4.3, §11

## 2026-09-03 — `benchmark reference lookup`
**Context**: docs/10's `benchmark()` pseudocode reads directly from the `nibud_reference` table to compare a household's spend against the Nibud reference for its household type. `packages/shared` has no database access (pure functions only, per the assignment's scope) and no I/O of any kind.
**Decision**: `benchmark(actual, reference: NibudReference)` takes the already-resolved reference row as a plain parameter instead of performing the lookup itself. The caller (an Edge Function or the mobile app, both of which do have DB access) is responsible for fetching the correct `nibud_reference` row for the household's composition/type and passing it in.

## 2026-09-03 — `trailing median population`
**Context**: docs/10's `trailingMedianDailySpend` needs a well-defined population (does a day with €0 spend count as a data point, or is it excluded?) and a window-boundary convention (does "today" count as part of the trailing window, or does the window end the day before?). Neither is stated explicitly; different choices materially change the computed median for a household with irregular spending patterns.
**Decision**: Zero-spend days are included in the population (a real day the household spent nothing is informative, not missing data) — outlier exclusion (top 2%) is a separate, explicit step and is not a backdoor for silently dropping zero-spend days. The window is `[today - windowDays, today - 1]` (ends the day *before* `today`, per `forecast.ts`'s `endsOn: addDays(today, -1)`) — "today" itself is always in-progress and its final total isn't known yet, so including it would bias the median toward partial-day figures. Separately, `median()`'s zero-length-window early return (`if (sortedAscending.length === 0) return 0`) is kept as an explicit branch rather than folded into a `?? 0` fallback on the odd/even index accesses, because for any *non-empty* array those accesses are proven in-bounds by the surrounding arithmetic — a `?? 0` there would be permanently-dead defensive code, worse than one guarded early return for a genuinely reachable (zero-day window) case.
**Consequence**: A household with several genuine no-spend days in its trailing window will see a lower median than if those days were excluded — this is the intended, more representative behaviour for a forecast input. Revisit if user testing shows this makes `safeToSpend`'s forecast component swing too aggressively for very irregular spenders.
**Specs touched**: docs/10 §6

## 2026-09-03 — income-ratio split's zero-income fallback
**Context**: docs/10 §7's `splitByIncome` falls back to an equal split "when total income is 0" per its own prose, but docs/11 §11's test-matrix wording ("income-ratio split with zero-income member") could also be read as "any individual member with zero income falls back to an equal split for everyone", which is a different and much more disruptive rule (one unemployed household member would silently defeat proportional splitting for the whole household).
**Decision**: Implemented the literal prose rule — `totalIncome === 0` (i.e. every member has zero income) triggers the equal-split fallback via `largestRemainder`. A single zero-income member alongside others with real income is handled correctly by the normal proportional formula without a special case: their `netMonthlyIncomeCents / totalIncome` ratio is legitimately 0, so their share is legitimately 0 (not equal to everyone else's) — the test matrix's "with a zero-income member" case is read as "the calculation must not divide-by-zero or throw for that member", which the normal `total === 0` guard already fully prevents.
**Consequence**: A household member who genuinely has no income is assigned €0 under income-ratio splitting unless the whole household has no income; if the product intent is instead "never assign a literal €0 to any one member", that is a distinct, undocumented product rule that would need its own spec update before implementing.
**Specs touched**: docs/10 §7, §11

## 2026-09-03 — safe-to-spend's `unknown` trigger & confirmation-filtering ownership
**Context**: docs/10 §5 requires `safeToSpend` to return `{ status: 'unknown' }` rather than a computed (and potentially wildly wrong) 0 "when there is no balance data at all", and separately notes that only user-confirmed (or ≥3-occurrence-stable) income counts toward the forecast — neither "no balance data" nor "confirmed" is a concept `packages/shared` can independently verify, since both require reading account-sync state and a user-confirmation flag that live in the database.
**Decision**: `{ status: 'unknown' }` is triggered purely structurally — `inputs.accounts.length === 0` (the caller passed no accounts at all) — rather than by any semantic "is this balance stale/trustworthy" judgement, which would require I/O this module cannot do. Likewise, every `IncomeEventInput`/`DueItem`-shaped input carries its own `confirmed: boolean` field, set by the caller before calling `safeToSpend`; the function itself only ever filters on that boolean (`e.confirmed && ...`) and never re-derives eligibility (e.g. by counting occurrences) — that occurrence-counting logic belongs to whatever queries `income_events`/`recurring_series`, outside this package.
**Consequence**: A caller that has real account rows but stale/never-synced balances will not get `unknown` from this function — it is the caller's job to decide whether to call `safeToSpend` at all in that situation, or to pass an empty `accounts` array deliberately to force `unknown`. Similarly, a caller that always passes `confirmed: true` defeats the "≥3-occurrence-stable" rule entirely; enforcing it is entirely outside this module's contract.
**Specs touched**: docs/10 §5

## 2026-09-03 — `ColumnMapping shape`
**Context**: docs/14 §2's import Edge Function contracts reference a "column mapping" the client sends when committing a manually-mapped CSV import, but no doc anywhere defines its concrete shape (which raw CSV header maps to which of our canonical transaction fields).
**Decision**: Invented `columnMappingSchema = z.record(z.string(), z.string())` — an open string-to-string map from raw CSV header name to canonical field name (e.g. `{ "Datum": "date", "Bedrag": "amount_cents", "Naam / Omschrijving": "description" }`). This is the minimal shape that satisfies "the client tells the server which column is which" without inventing canonical field names that aren't already established elsewhere in docs/14.
**Consequence**: If a future spec update defines a stricter shape (e.g. an enum of allowed canonical field names as the value type, or a nested per-column config object), `import.ts`'s schema and its `ColumnMapping` type both need revisiting — nothing else depends on its internal shape beyond "it's an object the client sends back verbatim".
**Specs touched**: docs/14 §2

## 2026-09-03 — enrich `structured-field tokenizer`
**Context**: docs/09 §2 step 4 gives per-field regexes with a lookahead up to the next known label (e.g. `Naam:\s*(.+?)(?=\s+(Omschrijving|Incassant|IBAN|BIC|NR):|$)`). Applied literally to the doc's own Zilveren Kruis worked example (`"...Incassant: NL42ZZZ33099220 Naam: Zilveren Kruis Machtiging: 123"`), the `Naam:` lookahead's stop-word list never includes `Machtiging` — so the literal regex cannot terminate the `Naam:` capture before `Machtiging:`, and would incorrectly capture `"Zilveren Kruis Machtiging: 123"` as the name instead of the doc's stated `"Zilveren Kruis"`.
**Decision**: Replaced the per-field-lookahead approach with a single label tokenizer: find every occurrence of any known label (`IncassantID|Incassant|Naam|Omschrijving|Kenmerk|Machtiging|IBAN|BIC|NR`) in one pass, then each field's value is simply the text between that label and the *next* label found (or end-of-string for the last one). This produces the same documented outputs for every worked example without needing an exhaustive, always-current stop-word list per field, and self-corrects if a new label type is added later (just add it to the one alternation).
**Consequence**: Any label not in the fixed alternation is treated as ordinary unlabelled text rather than a field boundary — acceptable since the alternation already covers every label named anywhere in docs/09 §2. `IncassantID` is listed before `Incassant` in the alternation specifically so the longer alternative wins (regex alternation is first-match, not longest-match).
**Specs touched**: docs/09 §2 step 4

## 2026-09-03 — enrich `unreachable-branch simplifications`
**Context**: Two spots in `enrich/` had a coverage-relevant conditional branch that is provably unreachable given how the module's own pipeline calls them, in the same class of issue as `budget/trailing-median.ts`'s `median()` fix: (1) `strip-prefixes.ts`'s `parseTrtpFields` looped `for (let i = 0; i + 1 < parts.length; i += 2)`, so `parts[i]` and `parts[i + 1]` are always in-bounds by the loop condition itself — a `?.trim() ?? ''` fallback there could never actually fall back. (2) `text-utils.ts`'s `titleCase` guarded against `word.length === 0` (from `.split(' ')` on a double-space-separated string) — but `titleCase` is only ever called from `deriveCounterpartyFromLeadingWords`, which is only ever called (via `normalize-description.ts`) on text that has already been run through `collapseAndTrim` (which collapses every run of whitespace to a single space before `deriveCounterpartyFromLeadingWords` ever sees it) — so a double space, and therefore an empty `.split(' ')` segment, can never actually reach `titleCase`.
**Decision**: In both cases, replaced the defensive fallback with a non-null assertion (`parts[i]!`, `parts[i + 1]!`) or removed the guard entirely (`titleCase` now does `word.charAt(0).toUpperCase() + word.slice(1)` unconditionally — safe even for an empty string, since `''.charAt(0)` and `''.slice(1)` both return `''`), each with a comment tracing exactly why the branch is unreachable, rather than writing a test that reaches into internal, non-exported behaviour to force a codepath the public API can never trigger.
**Consequence**: If `deriveCounterpartyFromLeadingWords` or `titleCase` are ever called directly with un-collapsed text from a new call site, `titleCase` will simply produce a run of single spaces in its output where the input had multiple (via `.join(' ')` after `.split(' ')`) rather than crashing — a graceful degradation, not a regression, should that assumption ever stop holding.
**Specs touched**: docs/09 §2 (no direct spec citation — an internal coverage/robustness decision)

## 2026-09-03 — `packages/shared` verification: `pnpm <script> -- --coverage` does not enable coverage under pnpm 10
**Context**: The literal verification command `pnpm --filter @kwartje/shared test -- --coverage` (this package's `test` script is `vitest run`) prints `> vitest run -- --coverage` and passes, but produces no coverage report and writes no `coverage/` directory. Root cause, verified empirically: pnpm 10.4.1 forwards trailing CLI args to the underlying script *including the literal `--` separator itself* (unlike some `npm run` versions, which swallow the first `--`), so Vitest actually receives one positional argument, the literal string `"--coverage"`, coming *after* its own `--` — Vitest treats everything after `--` as a positional test-name/file filter, not as a flag, so no test file matches that "filter" and coverage instrumentation is silently never turned on. Confirmed the fix: `pnpm --filter @kwartje/shared test --coverage` (no `--`) forwards `vitest run --coverage` and correctly produces the full coverage report.
**Decision**: Ran verification with `pnpm --filter @kwartje/shared test --coverage` (and the equivalent `npx vitest run --coverage` from within `packages/shared`) instead of the literal `-- --coverage` form, since the latter is a no-op under this repo's pnpm version. Did not change `packages/shared/package.json`'s `test` script (e.g. to a `test:coverage` script baking in `--coverage` directly) since that's a workflow convenience change beyond what a coverage bug fix requires, and could conflict with another agent's own package.json edits.
**Consequence**: Anyone (a person, CI, or another agent) copying the literal `pnpm ... test -- --coverage` form from an assignment brief verbatim will see all tests pass with no coverage failure ever reported, silently — worth calling out explicitly since a green run with no coverage table looks identical to "coverage checks were skipped for an unrelated reason" rather than "the --coverage flag never reached Vitest". CI configs invoking this package's tests with coverage should use the no-`--` form.
**Specs touched**: none (verification tooling only), `.claude/rules/07-testing.md` (100% branch coverage gate)
